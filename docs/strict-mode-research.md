# 严格模式解析差异调研（未验收）

2026-10-19 查阅官方资料，仅作为后续实现依据，不能代替本机 Typora 1.3.8 的 computer-use 基线。

- Typora 官方说明：https://support.typora.io/Strict-Mode/
- Lute 官方实现与说明：https://github.com/88250/lute
- 当前本地 Vditor 4.0.0 实现：frontend/node_modules/vditor/src/ts/markdown/setLute.ts。

Typora 严格模式主要涉及 GFM 语法约束：标题的 # 后需要空白，列表的续段与子列表需按列表标记宽度对齐。官方资料中的宽松模式则接受部分缺少空白的标题和较少缩进的列表。该说明当前页面更新晚于目标 1.3.8，版本差异必须实测。

上游 Vditor 的 setLute 没有对应完整严格/宽松模式参数。本地实现进展见下方。不能把高亮、上下标、公式等扩展开关的组合命名为严格模式；也不能在切换显示时直接改写用户的 # 或缩进，破坏原文基准。

需要完整验证缺空格标题、带转义 #、围栏/行内代码、引用中的标题，单/多位有序列表标记后的续段和子列表、混合列表与空行，以及编辑后保存往返。下述固定样本已验证，全部复杂组合仍未通过。

同轮补齐的“允许行内公式以数字开头”使用 Vditor 的独立 math.inlineDigit 参数，与严格模式没有替代关系。参数来源：https://github.com/Vanessa219/vditor#optionspreviewmath 。

## 2026-10-20 本机基线补充

已完成本机 Typora 1.3.8 启用/禁用严格模式的同文件对照，禁用后正常退出所有 Typora 进程并重启；结束时恢复启用、再次重启并截图确认。具体结果见 typora-strict-mode-baseline.md，两份实际可访问性树单独保存。

scripts/strict-parser-baseline.mjs 使用 Node vm 加载随包的同一固定 Lute 文件，直接读取原始样本字节并保存 HTML、源文件 SHA256、解析器 SHA256 和相关公开方法列表。当前样本的缺空格标题、两空格列表归属、10. 起始列表与续段结构与 Typora 严格模式观察相符；此结果仅为解析器诊断，不是桌面编辑、导出、撤销或全部严格模式验收。

实际宽松模式还将分离的列表重新归入同一有序列表，改变父子层级与显示序号。不能只添加“允许无空格标题”开关就命名为完整严格/宽松模式，也不能通过改写原始列表缩进伪装解析结果。下一步需为固定解析器提供可复现的容器/标题解析配置，并验证两种模式下的编辑和保存往返。

## 本地实现与验证

已为固定 Lute 增加实例级标题和列表规则，偏好设置 → Markdown → 严格模式控制即时渲染和 HTML 导出，保存设置立即生效。旧配置缺少该字段时保持严格模式。补丁和上游源码依据见 lute-patches.md。

实际桌面 44 项检查、独立副本保存并重新读取磁盘 4 项检查通过。初次检查发现渲染编辑会规范化未编辑的标题空格、列表缩进与序号；已使用编辑器序列化基线和原始 Markdown 的差量位置映射修复，指定文字变化后其余原文逐字符比较通过，撤销精确恢复。共同编辑路径的 211 项已有桌面回归通过。computer-use 另实际点击开关及保存，确认宽松标题显示和原文未变。

这些证据覆盖记录中的样本，尚不证明全部 GFM、复杂容器/列表续段、中文输入组合和全部导出格式对齐。另观察到该样本状态栏 MarkdownReader 为 95 字，Typora 为 93 字，字数统计差异待单独核对。
