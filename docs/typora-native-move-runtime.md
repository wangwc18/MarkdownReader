# Typora 实际图片移动复核（2026-10-24）

本轮恢复现有 Typora 1.3.8 窗口，通过原生“另存为”创建 `build/test-tools/native-move-runtime.md`，原来的 `typora-insert-rule.md` 未覆盖。以下结果是现场观察，不作为 MarkdownReader 移动功能的完整对齐证明。

## 重复引用样本

专用源 `native-move-source/移动样本.svg`，224 字节，SHA256 为 `CE24067E76F2CD4ADF3C6E436941B13A38681C7A58A53C78D9CD988142591713`。正文有两个完全相同的图片地址、一个带点路径和片段的别名、普通链接及行内代码。

通过格式→图像→移动图片到…实际提交 `native-move-result.svg`。原生保存框标题仍是“复制并更新图片路径到…”。保存后只有选中的第一处地址变为 Windows 绝对路径，标题保留；第二处、别名、普通链接和代码没有改变。目标字节与样本一致。保存后的原文保存在 `typora-native-move-duplicates-after.md`。

原始 fixture 路径的文件仍存在，但不能据此断言移动命令不会移除源：复测发现该窗口从原文档沿用了插入时复制规则，即使编辑删除了 YAML，点击新图片仍会将其复制到 `insert-rule-images` 并改写选中引用。因此首次动作的实际即时来源没有在对话框提交前单独核实，重复引用样本存在干扰，须重新测试。

## 单图片样本

将专用副本改为仅一个 `native-move-source/独立样本.svg` 图片引用。点击后可观察到地址自动变为 `insert-rule-images/独立样本.svg` 的绝对路径，且该副本实际存在，再执行“移动图片到…”至 `native-single-result.svg`。

保存后选中的地址为新目标绝对路径，标题保留，目标 SHA256 与上述样本一致。动作返回后及保存后的两次文件系统读取均看到 `insert-rule-images/独立样本.svg` 仍存在，原 fixture 也存在。这只证明当前带继承插入规则的窗口中的结果，不能推广到无规则的新窗口、所有扩展名或全部移动行为。

## 与工作区实现的差异及后续

MarkdownReader 当前单图片移动会解析并更新同源图片别名、移除经快照核对的源，并将文件操作纳入文档撤销历史。上述原生样本仅更新选中引用且保留所观察的源，两者不能记为已对齐。先在明确关闭插入规则的文档重测，再决定行为调整；不要根据受干扰样本直接改写文件事务。

本轮未执行原生撤销、批量移动、覆盖或跨盘，也未改动 MarkdownReader 的实现和预览 ZIP。原生文档当前保存为单图片样本。现有工作区批量移动 20 项实际检查仍仅代表固定样本通过。

## 后续重新载入尝试

图像偏好中观察到全局插入为“无特殊操作”，没有改动该偏好。通过文件→选择编码重新打开→UTF-8 重新载入已保存副本，选中图片的来源仍准确显示为 native-single-result.svg，再提交移动至 native-clean-result.svg。目标字节一致，保存后地址更新、标题保留，源 native-single-result.svg 仍存在。但随后图片上下文仍出现“复制到 insert-rule-images”，因此不能认定编码重开已清除全部窗口规则状态。

另创建完全无 YAML 的 native-move-fresh.md 并以本机安装程序打开，出现 License Info；提示关闭后的窗口清单没有新文档窗口，旧测试窗口仍在。未绕过激活，也未把未载入的新文档算作无规则比较通过。原生文档当前保存的引用为 native-clean-result.svg。上述重载结果仍不足以决定复制/移动事务的最终对齐方式。
